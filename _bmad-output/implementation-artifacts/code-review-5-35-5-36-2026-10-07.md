## Story 5.35 findings

### R1 — high — A Merge zone can hide a Crossing for the same pair

Sources: blind-hunter + edge-case-hunter + acceptance-auditor. Route: patch.

`Assets/RoadRage/Features/Vehicles/Traffic/Junction/JunctionConflictIndex.cs:103` discards subsequent zones for an already indexed movement pair. Sorting by ID makes the smallest-ID zone the sole retained kind and contact starts. `RoadModelValidator` validates each zone independently and permits the same pair in several zones; a valid Merge requires a shared exit, which does not prevent a separate Crossing containing that pair. A smaller-ID Merge plus a larger-ID Crossing is consequently exposed as Merge only. With sufficient holder ETA, `BlockedByGrants` can issue `GrantedMergeGap` despite the Crossing. This violates P10: every relevant zone must be Merge and any Crossing must block strictly.

Required action: retain all relevant zones, or conservatively aggregate pair facts so Crossing dominates and Merge admission checks the earliest applicable contacts. Test both ID orderings and all-Merge pairs with different contacts. This mixed-zone pair was not observed in the current MVP_Run model.

### R2 — high — Deadlock closure omits additional priority threats

Sources: blind-hunter + edge-case-hunter + acceptance-auditor. Route: patch.

`Assets/RoadRage/Features/Vehicles/Traffic/Junction/JunctionCoordinator.cs:645` checks closure only over the single cause returned by `YieldsToPriority` at `:619`. A request can have several priority actors with insufficient ETA, but only the first in TrafficId order is retained. Four waiting requests can therefore form a recorded cycle while a higher-ID external TooFar actor also threatens the chosen request. If internal causes sort first, the breaker grants despite that external cause. P3 requires every blocking cause to belong to W.

Required action: check all qualifying priority causes before declaring closure, and test input permutations. Use a distinct incoming corridor/control for the external actor so it is independently head of queue. A fifth follower on the same one-lane MVP approach would be queue-masked and is not a valid reproduction of this finding.

### R3 — medium — An empty control suppresses the entire junction's right-of-way

Source: blind-hunter. Route: patch.

`Assets/RoadRage/Features/Vehicles/Traffic/Junction/RightOfWay.cs:118` abandons the junction if any control lacks an approach; `TryApproachEnd` returns false for an empty controlled-movement list at `:171`. The validator permits an extra empty Uncontrolled control when other controls already cover every movement. Adding that otherwise accepted control to the crossroads empties its relation table, removing precedence between legitimate approaches and falling back to seniority. This violates P3's Uncontrolled right-of-way semantics.

Required action: reject an unresolvable approach explicitly, rather than silently discarding the valid junction's table. Cover an empty control and failure to resolve an approach.

### R4 — medium — A control spanning different approaches gets the first movement's heading

Source: blind-hunter. Route: patch.

`Assets/RoadRage/Features/Vehicles/Traffic/Junction/RightOfWay.cs:174` reads only `ControlledMovementIds[0].FromCorridorId`. Control ownership validation checks unique movement coverage and junction ownership, but imposes no consistency on the bound approach headings. A control binding northbound and eastbound movements is accepted, then both use whichever approach sorts first for every right-of-way comparison. P4 requires the actual approach heading.

Required action: validate that a control has a single unambiguous approach heading before constructing control-level relations, or calculate the relations at the actual movement-approach granularity. Test a control spanning differently headed corridors and order independence. No such control was observed in current MVP_Run.

### R5 — medium — Ordinary compilation accepts ambiguous right-of-way

Source: blind-hunter. Route: patch.

`Assets/RoadRage/Features/Vehicles/Traffic/Junction/RightOfWay.cs:129` records Ambiguous, but `RoadModelValidator.CheckControlKindsAndLines` does not reject such approach geometry. The explicit rejection exists only in `Migration/AuthoredRoadModel.cs:312`, after compilation. An otherwise valid uncontrolled intersection with headings near a sector boundary can be compiled directly, and the conflict index treats that pair as having no precedence. P4 requires a validation failure, not silent seniority fallback.

Required action: enforce the ambiguity check on the common validation/compilation path, with a direct compiler rejection fixture. The current MVP authoring pipeline already rejects ambiguity; this finding concerns the accepted general compiler input contract.

### R6 — medium — Traversal-pair facts required by D13 are recomputed each batch

Source: acceptance-auditor. Route: patch.

`Assets/RoadRage/Features/Vehicles/Traffic/Junction/JunctionCoordinator.cs:605` scans the Cartesian product of both traversals for each priority comparison to find the first threatening and last clearing movements. `:679` scans movement caps again. The index caches per-movement facts but not the relevant traversal-pair clearance facts required by spec P6/D13 and the completed Phase 3 task.

Required action: cache the model-derived traversal-pair conflict/clearance facts once per model and preserve numerical behavior. This is a structural spec gap, not evidence of a measured budget failure: the existing Gate C N8 p95 is 8.624 ms, below 10 ms. Do not turn this action into whole-system optimization.

### R7 — medium — Successful MergeGap has no proof through real builder reports

Source: verification-gap. Route: patch.

`Assets/RoadRage/Tests/EditMode/Story535JunctionRulesTests.cs:554` proves successful admission with manually assembled movement distances and statuses. The runtime derives those fields at `JunctionRequestBuilder.cs:107`. Scenario G's assertions at `Tests/PlayMode/Story535JunctionPlayModeTests.cs:449` require waiting and eventual service, not service while an incompatible holder remains. Both its completed 2026-10-06 evidence and the Gate C campaigns report `GrantedMergeGap 0`. Consequently, incorrect real ETA inputs that always reject a sufficient gap can pass every checked live scenario. The acceptance matrix explicitly requires a distant holder to allow MergeGap and subsequent following without contact.

Required action: add a deterministic scenario using real tracked poses/routes and the report builder, require GrantedMergeGap before the holder releases the conflicting movement, then verify both vehicles clear without contact. Preserve the existing insufficient-gap scenario.

### R8 — medium — Lined movement queue masking lacks a two-actor regression

Source: verification-gap. Route: patch.

`Assets/RoadRage/Features/Vehicles/Traffic/Junction/JunctionRequestBuilder.cs:263` adds queue masking for actors inside a movement but before its stop line. The existing masking fixture uses an unlined approach; `Tests/EditMode/Story535StopLineTests.cs:239` checks that an actor alone is head of queue. Removing the new movement-occupant check would incorrectly admit a follower already inside the lined movement without failing these assertions.

Required action: place two actors beyond the generic entrance but before b and assert the follower's HeadOfQueue=false, MaskingActorId=leader and NotHeadOfQueue rejection, including a route truncated by replan. This is a coverage gap; the inspected production guard is present.
