### R1 — Rear clearance can miss an actor already intersecting the sweep

**Source:** blind-hunter + edge-case-hunter. **Route:** patch. **Requirement:** R5 (`RearBlocked` for a frame actor in the rear sweep).

`RecoverySupervisor.cs:334` expands the sweep by the greatest footprint half-extent, without accounting for actor orientation. That is not a conservative projection of a rectangle: half-length 2.22 m and half-width 1.03 m yield approximately 2.447 m along an axis at a suitable rotation, exceeding the 2.22 m expansion. With self rear extent 2.22 m and reverse travel 3 m, an actor centered 7.60 m behind can project into the swept region ending 5.22 m behind, while the current center cutoff is 7.44 m. `:337` also discards every actor whose reference point is ahead, even when a sufficiently long or rotated footprint extends into the rear sweep.

This is a false-clear result at acceptance, distinct from the approved deferral of repeated rear checks during the maneuver. The driver feeds this result directly into `SubmitRecovery` at `TrafficV2VehicleDriver.cs:779–781`; a false-clear therefore accepts the reverse rather than returning `RearBlocked`.

**Correction:** compare the two oriented footprints against the swept rear rectangle, or use a conservative support bound with footprint intersection along both axes. Do not require the other reference point itself to be behind. Preserve the approved frame-actors-only scope and do not add continuous rear perception.

**Verification to add:** rotated actor whose corner overlaps beyond the current cutoff; actor with a reference point ahead but footprint occupying the swept rear region; nearby disjoint actor. Extend the existing pure geometry fixture, then run Story539 EditMode.

### R2 — Four failed maneuvers need not exhaust recovery

**Source:** acceptance-auditor. **Route:** patch. **Requirement:** R4 and AC3.

`RecoverySupervisor.Observe` records a completed maneuver at `:194–200` without applying the exhausted-attempt rule. If the fourth failure is followed by a nominal step with a legitimate blocker, `ProgressExpected` returns false and `Cause` becomes `None` (`:210–214`, `:291–293`). `TryRequest` returns for `Cause == None` at `:232` before checking `EpisodeAttempts >= RecoveryMaxAttempts` at `:233–236`.

The vehicle can remain Active indefinitely despite four failed maneuvers. If ordinary progress later resumes, `Observe` can reset the exhausted budget after 0.5 m (`:217–223`), granting another episode without the required terminal transition. This case is reachable when a leader or junction wait appears as the fourth maneuver ends. The existing exhaustion test always supplies a collision goal in `AwaitingRecovery` after each failure (`Story539RecoveryTests.cs:238`), keeping the cause eligible and masking the early return.

**Correction:** apply exhaustion when the final failed attempt completes, independently of a new recovery cause, before nominal progress can erase the exhausted episode. Preserve a successful maneuver's completion/exit semantics and all declared thresholds.

**Verification to add:** fourth `Stalled` or `NoProgress` outcome followed by a legitimate blocked nominal state; subsequent progress must not revive an already Faulted vehicle. Run Story539 EditMode and the driver PlayMode fixture.

### R3 — Faulted does not protect the portal removal path

**Source:** blind-hunter + edge-case-hunter + acceptance-auditor. **Route:** patch. **Requirement:** R7, D6 and AC3.

`TrafficV2VehicleDriver.HasReachedExitPortal` checks only the exit flag and tolerance latch (`:496`). The localization stage continues setting the exit flag while Faulted (`:757–758`). A vehicle faulted through the ProgressDeficit path can have a clear tolerance latch. If an external physical push carries it along its reference through its portal, it reports completion despite its terminal lifecycle state.

`PortalTrafficSpawner.ReleaseVehiclesAtExitPortals` consumes that property at `:364`, removes the object from live traffic at `:369`, and despawns it at `:380`. The new Faulted compose fallback (`TrafficV2VehicleDriver.cs:971–975`) does not guard this consumer. This contradicts the permanent stay-present contract until the deferred catastrophic cleanup policy. The production spawner was unchanged, but the newly introduced lifecycle must protect its existing removal contract.

**Correction:** make the driver's portal-completion contract exclude Faulted, including the frame on which faulting and portal detection coincide. Preserve ordinary active-vehicle portal exits.

**Verification to add:** fault the real V2 driver, then supply a physically reached exit while its latch is clear; assert portal completion remains false and no spawner removal occurs. The current injected Faulted proof keeps the same pre-exit state and never exercises this consumer.

### R4 — Forward braking before reverse is not verified

**Source:** verification-gap. **Route:** patch. **Requirement:** R5 and the stated composer verification task.

`Story539RecoveryTests.cs:389` checks nonnegative motor torque while moving forward above `MinimumDirectionSpeed`. `VehicleTireModel.ResolveWheelDriveTorque` returns zero above that threshold regardless of the service brake input (`:236`). The assertion therefore passes both with correct braking and with no braking.

For example, a regression setting the forward-speed capacity branch of `VehicleDriveIntentComposer.cs:243` to zero would emit zero brake input at `:245`, but still satisfy that assertion. The driver proof's helper fixes measured speed to zero (`Story539RecoveryPlayModeTests.cs:223`), so it never covers the forward-speed branch either. This is a verification gap, not a claim that current forward braking is broken.

**Correction:** strengthen the existing forward-speed cases to require positive brake input and positive service braking torque through the actual tire-model conversion. Keep the existing no-throttle/no-reverse-motor-torque assertions. Run Story539 EditMode; no new wrapper or Editor probe is needed.
