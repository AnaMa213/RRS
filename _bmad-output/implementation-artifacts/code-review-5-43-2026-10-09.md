## Findings

### R1 — Medium — permitted zero b_safe rejects the speed plan

Sources: blind-hunter + acceptance-auditor. Constraint: E4, `b_safe >= 0`, effective behavioral braking and continuous modulation.

`EmotionGains.TryValidate` accepts a SafeBrakingLimit gain of -1 (`EmotionModulation.cs:44`), so a governing weight of 1 gives an effective braking limit of zero (`DriverModel.cs:183`). Other parameters and the authored braking limit can remain ordinary positive values. `DrivingPolicy.Resolve` accepts this policy because `LeversFinite` accepts zero (`DrivingPolicy.cs:182`).

The driver passes the effective profile into `SpeedPlan.Build` (`TrafficV2VehicleDriver.cs:943`). The latter constructs `LongitudinalBounds` from effective a and b_safe (`SpeedPlan.cs:225`), whose `Valid` requires strictly positive deceleration (`MotionPlan.cs:38`). Thus the permitted boundary returns `SpeedPlanIssue.InvalidInput` (`SpeedPlan.cs:232`) and becomes `V2FallbackReason.ProfileRefused` (`TrafficV2VehicleDriver.cs:949`). The vehicle enters the safety fallback rather than handling the declared behavioral domain. This also happens if v0 is deliberately zero at the same time.

Required action: make the declared zero-braking boundary coherent through planning/command consumers while preserving physical safety and authored fallback braking. Do not silently change the frozen gain/domain requirement to exclude zero. Add an end-to-end pure planning regression for gain -1 at full governing weight, including deliberate v0=0. Current domain assertions only examine resolved scalars; the existing planning immobilization test leaves b_safe positive.

### R2 — Medium — invalid raw meters bypass the whole-reading Calm rule

Sources: blind-hunter + verification-gap + acceptance-auditor. Constraint: E5 and the explicit nonfinite matrix case.

`EmotionMeters.Read` normalizes each meter with `Percent` before constructing the shared reading (`EmotionMeters.cs:77`). `Percent` replaces each nonfinite value individually with zero (`:106-108`). Therefore `EmotionReading` never sees the original invalid value and cannot apply its whole-reading Calm guard.

Concrete producer path: with valid tuning, `Change(default, NaN, 80, tuning)` treats rage percent as zero and opens Escape; `Read` produces `(0, 0.8, Escape)` with a fear weight of 0.8 instead of Calm. Alternatively, after `NetworkedRageState.ApplyRageDelta(60, tuning)`, a nonfinite FearValue leaves `CurrentEmotion` with rage weight 0.6. This is precisely the malformed reading boundary E5 requires to fail closed. The existing test at `Story543EmotionModulationTests.cs:202` constructs `EmotionReading` directly, bypassing the faulty producer.

Required action: reject either nonfinite raw meter before normalization/arbitration and return the whole Calm reading. Cover NaN and infinities on both channels through `EmotionMeters.Read` and the actual `NetworkedRageState` producer; finite out-of-range values should still be bounded as specified.

### R3 — Medium — fear-driven lever formulas lack regression assertions

Source: verification-gap. Constraint: Execution task requiring continuity/monotonicity per lever and E4’s formula for both channels.

`EveryLeverIsAContinuousMonotonicFunctionOfTheGoverningWeight` checks the rage formula for every lever (`Story543EmotionModulationTests.cs:249`), but fear cases assert only headway and risk (`:270`). Domain checks and governor-isolation comparisons do not establish the numeric fear formula. A hypothetical change replacing `fear.DesiredSpeed` by zero in `DriverModel.cs:176` would leave these assertions satisfied while removing required fear-driven speed modulation. This mutation is an analytical counterexample, not an executed experiment.

Required action: assert the fear formula across governing weights for every lever, including speed, s0, a, b, b_safe, accepted gap and maneuver costs. Use distinct, nonzero authored gains so zero default gains cannot conceal wiring mistakes, and verify saturation/clamping where relevant.

### R4 — Medium — host fear-decay publication is unverified

Source: verification-gap. Constraint: E1/E3 and the host integration execution task.

The pure kernel test asserts fear decay (`Story543EmotionModulationTests.cs:71`). The host integration test checks FearValue immediately after applying a delta (`:408`) and later advances 60 seconds (`:415`), but observes only rage after that advance. Removing `FearValue.Value = meters.Fear` from `NetworkedRageState.Advance` (`NetworkedRageState.cs:75`) would preserve the existing assertions while preventing future calls from seeing decayed fear. The network publication and resulting escape exit need their own regression assertion. This deletion is an analytical counterexample, not an executed experiment.

Required action: apply fear 60 with rage below it, advance 31 seconds, assert published fear 29 and governor Rage, then advance again and confirm subsequent decay starts from 29. Observe both `FearValue.Value` and `CurrentEmotion`.

### R5 — Low — finite underflow bypasses strictly positive a/b domains

Sources: edge-case-hunter + acceptance-auditor. Constraint: E4, a and b strictly positive after modulation.

Authoring accepts any finite positive a or b (`DriverProfileDef.cs:118-128`), and modulation accepts any finite gain strictly greater than -1 (`EmotionModulation.cs:47-49`). For an authored value of `1e-38f`, gain `-0.99999994f` and governing weight 1, the product at `DriverModel.cs:179-180` rounds to zero. `DrivingPolicy.LeversFinite` checks only finiteness (`DrivingPolicy.cs:186-192`) and accepts zero. This is an extreme authored input, not a default-profile failure, hence low severity.

Required action: validate effective strict-positive domains alongside finiteness and apply the existing authored-policy fallback when underflow violates them. Add a bounded numerical-domain regression; keep calm bitwise invariance.

## Dismissed claims

Eight distinct claims were dismissed, not deferred:

1. Direct calls to the continuous DriverModel kernel can overflow: the production caller is `DrivingPolicy`, whose new finiteness guard already restores the authored policy. No additional production caller of the overload was found.
2. Same-tuning direct NetworkVariable writes leave tier stale: no production writer bypassing the standard state methods was found. The fixture's supported initialization is before tuning has been applied; general live direct-write synchronization is not an acceptance requirement.
3. Direct fear writes leave escape stale: same unsupported live mutation assumption; standard delta/advance paths update hysteresis.
4. Directly lowering held rage skips a decay step: standard explicit negative deltas release the hold immediately, as required by E2. General direct mutation is not the specified path.
5. Swapping maximum values at runtime retains old hold state: no runtime tuning-switch policy/caller is delivered by this story. A general maximum-transition contract would broaden scope.
6. A no-op reaction can select tuning: the new reading intentionally becomes available when tuning is applied; V1 values remain unchanged. No demonstrated violation of the specified V1 invariance.
7. Adding a source after Awake needs automatic recaching: Awake caching is explicitly required and already an accepted boundary; production prefab integration is in 5.44.
8. Fallback command behavior needs a new emotion comparison fixture: this diff changes which scalar enters an unchanged composer. The exact authored-input structural assertion verifies that changed boundary; no changed composer algorithm or concrete regression was shown.

Max-hold release while a tier freeze remains is consistent with the separate E1 freeze. Caching the authored fallback input is distinct from retaining a first-step modulated input; no new current-profile replacement requirement was inferred. Production tick, prefab/MVP_Run integration, DesiredSpeedAt application, pooling and source replacement were not added to the review scope.
