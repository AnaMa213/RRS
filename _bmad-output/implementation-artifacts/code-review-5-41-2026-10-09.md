## R1 — Acceptance while already inside the scope has no termination regression proof

**Source:** blind-hunter. **Requirement:** P4, termination on scope exit. **Location:** `Assets/RoadRage/Tests/EditMode/Story541DrivingPolicyTests.cs:310–322`; production initialization at `TrafficRuleAuthority.cs:154–156`, termination predicate at `:131–135`.

The scope-exit fixture accepts its request while A is on C1, outside the requested C0 scope. A later batch observes A on C0 and sets `Active.Entered` there. This proves entry after acceptance, but not acceptance when the requester is already inside its scope.

The current production initialization correctly sets `Entered` at acceptance. Replacing just that initialization with `false` would leave the existing scope-exit fixture unaffected: its later C0 observation still sets the flag. In the uncovered scenario, A is on C0 when accepted at N and on C1 at N+1. That regression would publish `Held` at effective N+2 instead of `Ended ScopeExited`; without a return to C0, the exception would persist until expiry. This is a source-based counterexample, not an executed mutation test or a claim that current code is defective.

**Correction:** add a Story541 EditMode scenario accepting a ScopeExited request while A is localized on C0. Prove it is effective at N+1. At the very next batch, report A localized on C1, with expiry sufficiently later to isolate scope exit. Require `Ended ScopeExited`, source N+1/effective N+2, no effective exception at N+2, and zero active exceptions. A following batch must not publish the termination again. Preserve the existing outside-then-entered case.
