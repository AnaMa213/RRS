### R1 — Preserve the route and displacement reference during collision response

`TrafficV2VehicleDriver.Step` calls `PlanningSpine.Evaluate` at line 740 and adopts replanned routes at line 757, before the new collision analysis/submission/update at lines 814–819. These earlier blocks have no collision-goal guard. The new latch suspension at lines 658–663 removes the previous tolerance fallback barrier during contact and active goals.

This is reachable when a collision moves a vehicle onto another corridor: `RoadLocalizer.Localize` searches the current spatial cell globally; `RoutePlanner.TryReuse` cannot reuse the original route if the localized corridor is absent from its reachable occurrences; `Core` therefore replans. `AdoptRoute` rebuilds `ReferenceTrack` with the previous angular offset, not the previous lateral displacement. Subsequent `PrepareStep` measures d against the new reference. A vehicle aligned on the new corridor can then satisfy d <= epsilon_t and resume instead of awaiting physical recovery from the original reference.

This violates Never's exclusion of reattachment/replanning and weakens C6/AC3. Guard route adoption from the first significant contact and throughout the collision goal; preserve the displacement reference until the authorized recovery owner takes over. Cover the actual driver sequence with a categorized fixture, without changing the scene, prefab, thresholds or existing assertions.

### R2 — Publish the terminal tactical transition

At `TrafficV2VehicleDriver.cs:815`, a frame without a significant contact sets `LastTacticalResponse` to null. `TacticalDecision.Update` can then end the goal with `Resumed` or `ExitPortalReached`, making `Active` false. `DriveOutcome` at line 1089 checks only `Active || LastTacticalResponse.HasValue`, so it sends null on that termination frame. The tactical object retains the reason, but the required outcome/projection never renders it.

Publish the tactical text when a goal was active on entry to the update as well as when it remains active or receives a request. Test both termination reasons through the driver's outcome publication. This addresses C7 without displaying stale terminal text forever.

### R3 — Preserve the invalid-facts handshake

The matrix requires nonfinite facts to produce `InvalidRequest` and no goal. `CollisionPredicates.Significance` at `CollisionResponse.cs:91` returns `None` for nonfinite facts; `CollisionAnalysis.Analyze` at lines 208–210 consequently returns null. The driver then skips `Submit`, leaving no refusal reason. The test at `Story538CollisionResponseTests.cs:131` directly constructs a malformed request and verifies `Submit`; it never verifies the analysis-to-submission path that production uses.

Preserve the pure significance predicate's result while making analysis surface invalid facts as a versioned request that the tactical boundary rejects. Add an analysis-to-submission test confirming `InvalidRequest`, no active goal, and the published response. No new threshold or safety verdict is needed.

### R4 — Credit stability only after braking was applied

`TacticalDecision.Update` at lines 177–187 advances the reaction timer, changes `Phase` to `Braking`, then immediately adds dt to `stableSeconds`. In production, `Update` runs before `CommandFor`, so the facts being credited on the transition describe the preceding reacting timestep. When the stability threshold is subsequently reached, `Update` ends the goal before issuing that frame's braking command. At dt = 0.02, the code can resume after 0.48 seconds of actual braking despite the implementation's recorded guarantee of at least 0.5 seconds after the reaction.

`AReactionIsAlwaysFollowedByBrakingAndAFrontalEvasionBrakesAtOnce` uses command-before-update ordering and accepts `StableSeconds - Dt`, so it does not enforce this guarantee. Credit elapsed stability according to the phase that governed the preceding physical step, and test the production update-before-command ordering. Keep C6's 0.5-second threshold unchanged.
